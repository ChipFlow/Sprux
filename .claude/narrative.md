# Project Narrative: BaSpaCho

## Summary

BaSpaCho (Batched Sparse Cholesky) is a high-performance direct solver library for sparse symmetric matrices, implementing supernodal Cholesky decomposition with GPU acceleration backends. We're expanding it from pure Cholesky to support general linear system solving via LU and LDL^T factorization across CPU and GPU platforms.

## How It Works

The library treats sparse matrices as block structures in CSR format. Core concepts:
- **SparseStructure**: Block indices in CSR format (`ptrs`, `inds`)
- **CoalescedBlockMatrixSkel**: Hierarchical blocking with spans (basic groups), lumps (aggregated spans), chains (span rows × lump cols), and boards (full lump blocks)
- **Solver Interface**: Creates solvers via `createSolver()`, supports multiple backends (`BackendFast`, `BackendCuda`, `BackendMetal`, `BackendOpenCL`)
- **Operations**: `factor()` for decomposition, `solve()`/`solveL()`/`solveLt()` for triangular solves, with `factorUpTo()`/`solveLUpTo()` for partial operations on marginals

The supernodal approach groups blocks into larger computational units for better GPU utilization. Each backend implements block-level operations differently—CUDA with native kernels, Metal with compute shaders + MPS matrix operations, OpenCL via CLBlast library. GPU operations use threshold-based hybridity: large matrices offload to GPU, small matrices remain CPU-based when dispatch overhead exceeds computation time.

## Dragons & Gotchas

- **Metal Float-Only Precision**: Apple Silicon lacks native FP64. Metal backend float-only; double precision intentionally errors. User code documentation critical.
- **GPU Dispatch Overhead Requires Threshold-Based Hybridity** (c2b751a, bdd0f77, b4f93c3): Blindly GPU-offloading harms performance on small matrices—dispatch overhead exceeds computation. potrf needs n ≥ 32, trsm needs n²k ≥ 64³ for GPU benefit. Smaller ops faster on CPU (Eigen). Each GPU operation needs parameterized testing across size ranges to find optimal threshold; GPU acceleration is selective offload, not "replace CPU everywhere." Hybrid execution on unified memory (Apple Silicon) validates this pattern: CPU BLAS on small lumps (n≤256), GPU on large. Threshold tuning per-operation (BASPACHO_MPS_POTRF_MIN_N, BASPACHO_METAL_CPU_BLAS_THRESHOLD) essential for performance portability.
- **Metal Encoder Lifecycle Coupling** (c2b751a): MTLCommandBuffer and MTLRenderCommandEncoder tightly coupled. MPS operations end encoder; reusing it crashes. Decouple buffer allocation (once) from encoder creation (per-operation). Metal GPU code must respect encoder boundaries—don't assume state persists across heterogeneous operations (custom kernels + MPS).
- **Block Structure Interaction with LU**: Schur complement updates interact subtly with coalesced block boundaries (spans, lumps, chains). Row-by-row strategies fail across lump boundaries. Multi-block test matrices essential.
- **GPU Dispatch Overhead Dominates Small Ops**: Command buffer overhead substantial—300 3×3 blocks generate 4.39M saveGemm dispatches. Batching reduces 70× (8ed0870). Small kernels across many blocks require aggressive batching before kernel optimization is worthwhile.
- **Batched Kernels Need Inter-Thread-Group Sync**: Fusing N kernels requires proper synchronization design. Commit 8dd9e8b: multiple thread groups writing shared buffers need GPU-wide barriers (`memoryBarrier` + `threadgroupBarrier`), not just intra-group `simdgroup_barrier`. Thread group interference causes NaN/inf results without proper sync.
- **Backend-Specific Floating-Point Rounding**: BLAS, CUDA, Metal, OpenCL each accumulate error differently. Tests use generous tolerance bands; OpenCL double-precision deliberately relaxed (508f01e). Inherent to different compute implementations, not bugs.
- **Kernel Porting Is Not Translation**: Metal and CUDA expose different parallelization models. CUDA→Metal porting requires algorithm rethinking, not syntax conversion (commits 55948b7, d9abcd9).
- **Real-World Benchmarking Catches Performance Issues**: Synthetic test matrices miss bottlenecks that appear at scale or in irregular sparsity. Circuit/physics Jacobians expose block traversal, memory layout, GPU scheduling issues. c6288 circuit (25k×25k, 97k nnz) is profiling target of choice—optimize there, not toy matrices.
- **Preprocessing-First Architecture Beats Post-Factorization Perturbation** (e406e6a, 62d4b3d): AMD (Cholesky-optimized) reordering produces ~40% zero/near-zero pivots in circuit Jacobians. Attempted post-factorization static pivoting (perturbation) but failed—accumulated errors cascade through Schur complements, causing NaN. Root lesson: reordering and factorization algorithms must align structurally. Solution: MC64 preprocessing (BTF transversal + equilibration) reshapes matrix upfront. C6288 Jacobians now solve robustly: preprocessing → LU → ~20 iterative refinement steps → 1e-11 residual (vs. NaN before). Preprocessing cost amortizes after ~3–5 solves; cost ~1–2% of total for multi-solve sequences. Static pivoting remains useful as diagnostic (exposing pivot quality issues) but shouldn't be primary stability mechanism. Lesson: for robust sparse LU on diverse problems, preprocessing is non-optional tier, not fallback option.
- **GPU Kernel Optimization is Iterative: Correctness → Profile → Refactor** (4a0afbb, d4ff88a): Validated across sparse elimination factorization (50× gain) and solve (240× gain). Initial kernel implementations were functionally correct but suboptimal. Profiling on real matrices revealed bottlenecks not obvious from algorithm pseudocode: memory access patterns, threadgroup synchronization overhead, work distribution imbalance. Each refactoring iteration targeted one specific bottleneck, yielding cumulative dramatic gains. Notably, different operation types (factorization vs solve) have vastly different optimization potentials—bandwidth-bound operations (sparse triangular solve) show 4.8× higher gains than compute-bound ones (GEMM-heavy factorization). Lesson: don't expect first-pass kernels to be performance-optimal. Design for correctness, profile on real matrices to identify bottlenecks (memory bandwidth saturation? synchronization overhead? dispatch latency?), then refactor systematically. GPU backend development is fundamentally iterative—optimization potential varies wildly by operation type. Premature micro-optimization based on folklore wastes effort.

- **GPU Sync Overhead Is Layered, Not Monolithic** (5c82c1e, 7eda82c, 8023322): Dispatch overhead isn't a single bottleneck but layered: per-operation GPU dispatch → per-buffer GPU memory operations → per-phase synchronization points. Addressing layers sequentially yields cumulative gains: command-level batching (7.6×) + buffer batching (+22%) = 4.3× end-to-end improvement. Recent CUDA porting (8023322) validates pattern on stream model: GPU-resident pivots + deferred readback consolidate phase-level sync, matching Metal's optimization strategy. Each fix is 10–20 lines of code. Lesson: don't assume single optimization solves layered overhead. Measure incrementally, identify highest-overhead layer, fix systematically. This pattern applies across GPU backends—sync overhead is architectural, not platform-specific. CUDA and Metal expose it differently (streams vs command buffers) but solutions are isomorphic.

- **GPU Library Selection Thresholds Vary Dramatically by Size** (dabeed2): On Apple Silicon, MPS Cholesky is fast for medium sizes (4-128) but 16× slower than BLAS spotrf for large matrices (n=2766). Blindly GPU-offloading to MPS or defaulting to Eigen CPU harms performance. Solution: three-tier routing (Eigen for tiny, MPS for medium, BLAS for large) with size-specific thresholds. Same pattern applies to trsm—MPS optimal at certain n²k ranges, BLAS better elsewhere. Extended to CPU-GPU hybrid execution (bdd0f77, b4f93c3): below threshold (n≤256), use CPU BLAS on unified memory (no GPU memcpy); above threshold, use GPU. Lesson: GPU acceleration requires profiling the library implementation across size ranges. Different libraries have different strength zones. Each GPU operation (potrf, trsm, GEMM, sparse kernels) needs parameterized testing to identify optimal library/platform selection thresholds—this is not one-size-fits-all, but problem-size-dependent and architecture-aware.

- **Batch Metal Sparse Elimination Dispatches** (709c447): Extended multi-layer batching pattern to sparse elimination phase. Virtual methods `doAllEliminationsLU()` / `doAllEliminations()` on NumericCtx with default per-level fallback. Metal override encodes all level-set factor+elim kernels into single command buffer via `encodeKernel()` pattern, with memory barriers between dispatches and single `commitAndWait()` at phase end. Also batches Cholesky `doElimination()` for GRID/MERI problems. Solver.cpp fast path calls batched method; partial factorization (marginal computation) falls back per-level. **Result: LU factor 7.3ms → 4.9ms (1.5×)**—20 command buffers consolidated to 1. Validates that batching pattern generalizes across all solver phases (symbolic, factor, solve, refinement). Remaining factor-phase gap (vs ~2ms theoretical) is CPU-side overhead (maxDiag computation, dense loop setup). Demonstrates that GPU overhead elimination is architectural, not isolated to single phases.

- **Pre-Computed Work List for LU Sparse Elimination** (2778e25): Optimization exploration attempting to reduce GPU kernel complexity. Replaces divergent binary searches (finding L/U row offsets in sparse structure) with CPU pre-computed LUWorkItem list (int32 offsets). New kernel: 3 buffer bindings vs 16 original. **Performance: neutral** on c6288 (7.6ms vs 7.4ms baseline). Binary searches on Metal constant memory are already fast for scalar blocks—SIMD-uniform search has zero divergence. Target-sorted dispatch hurts (disrupts L/U read locality; increased factor 7.4ms → 8.2ms). Key insight: Metal constant memory broadcasts are heavily cached; within-warp reads are nearly free. Divergent binary search cost was overestimated. Learning: before "simplifying" GPU kernels, profile actual performance impact. Simplification often trades complexity for worse cache behavior.

## Open Questions

- **Remaining Per-Lump Dispatch Overhead in Solve** (next frontier): Sparse elimination dispatch overhead now consolidated at phase level (709c447), but solve still launches 25K per-lump GPU kernels for sparse triangular operations (~1s of ~1.5s total c6288 LU time). Options: (1) CPU sparse triangular solve for small lumps (CPU threshold pattern from dense ops), (2) level-set grouping reusing schedule from Milestones 1–2, (3) across-lump kernel fusion (multi-lump sparse ops in single kernel), (4) hierarchical dispatch batching at level granularity. Profiling (BASPACHO_PROFILE_LU) identifies exact launch overhead per lump. Next optimization cycle should target solve phase bandwidth-bound operations—empirically showed 4.8× higher optimization potential than factorization.

- **CUDA Async Transfer Payoff Thresholds**: Pinned memory + async H→D transfers (5e6fbcc) reduce dense loop latency. Where is the crossover point vs synchronous memcpy? BASPACHO_PROFILE_LU env var now enables measurement—matrix-size sweep would reveal amortization thresholds. Recent CPU BLAS fallback (3406632) may eliminate need for async mechanics on small dense lumps.

- **Extended Preprocessing for LDL^T**: MC64 preprocessing optimizes LU pivot quality. Can similar techniques improve LDL^T stability on indefinite systems? SuiteSparse AMDL is indefinite-optimized—how does MC64 + AMDL compare to pure AMDL? Preprocessing module abstraction supports extension.

- **Metal MTLDispatchTypeConcurrent Revisit**: Initial attempt (4e7fcf2) failed due to data corruption from missing event synchronization. Now that we understand MTLEvent requirements, concurrent dispatch for level-sets with proper event signaling might unlock parallelism. Would require 2–3 weeks design/validation; only pursue if profiling shows dispatch overhead dominates remaining time.

- **OpenCL GPU Implementation Completion**: Currently CPU fallback-only. Full GPU kernels needed, or CUDA/Metal provide sufficient coverage for target use cases?

- **Metal FP64 Strategy**: Float-only is hard constraint on Apple Silicon. Software-emulated double or alternative architecture (CPU FP64 + GPU float for large operations)? Determine acceptable penalty for production circuit simulation.

- **Per-Block Adaptive Thresholds**: GPU thresholds (BASPACHO_MPS_POTRF_MIN_N, BASPACHO_METAL_CPU_BLAS_THRESHOLD) are global constants. Would per-block adaptive thresholds (based on actual block size distribution in matrix) improve throughput? Profiling data from irregular block matrices (GRID, circuit Jacobians) should guide per-block tuning.

- **True Multi-Structure Batching**: Current architecture is single-structure (one sparsity pattern, multiple RHS/systems). Extending to multi-structure (diverse patterns in same dispatch) requires scheduling/memory-layout redesign. MC64 preprocessing enables robust LU across problems—could unlock ensemble solves in optimization/sensitivity analysis workflows.
