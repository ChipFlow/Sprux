# Learnings: BaSpaCho

### Block Structure Interaction with LU Schur Complements (2026-02-23)
**Insight**: LU factorization's Schur complement updates interact subtly with coalesced block structures (lumped spans, chained rows/columns). A straightforward row-by-row update strategy that works for single blocks fails when blocks span multiple lumps.

**Context**: Commit 49f264a fixed a multi-block LU bug where Schur updates weren't respecting the coalesced block boundaries. This required careful reasoning about how span groupings map to computational order. When implementing LU on new backends (Metal, CUDA), this same structure complexity had to be replicated in kernel design—you can't just port single-block BLAS calls directly.

### GPU Backend Precision Tolerances Vary Significantly (2026-02-23)
**Insight**: Different compute backends (BLAS, CUDA, Metal, OpenCL with CPU fallbacks) produce measurably different floating-point results for the same operations. This isn't about wrong implementations—it's rounding accumulation from different BLAS libraries, compiler optimizations, and instruction sets.

**Context**: Commit 508f01e relaxed OpenCL double-precision tolerances because the experimental backend's CPU fallbacks accumulate error differently than native GPU implementations. When validating against UMFPACK, tests need generous tolerance bands. This becomes critical for stability-sensitive operations like LU factorization—tight tolerances will cause spurious test failures across backends.

### Metal Kernel Implementation Requires Different Block Traversal Order (2026-02-23)
**Insight**: Metal compute shaders expose a different parallelization model than CUDA. The same block-level algorithm (e.g., LU with Schur complements) maps to Metal kernels with different thread group sizes, memory access patterns, and update ordering. Blindly porting CUDA kernels to Metal fails.

**Context**: Commits 55948b7 and d9abcd9 implemented LU kernels for Metal. Metal uses `simdgroup_barrier` and fixed threadgroup sizes, forcing a reorganization of how blocks are processed compared to CUDA's flexible threading. This wasn't a simple translation—the algorithm itself needed rethinking for efficient Metal execution.

### Batched Solving Is Architectural, Not Just Algorithmic (2026-02-23)
**Insight**: "Batched" in BaSpaCho is a top-level design choice (multiple matrices share structure, solve together) rather than something you add incrementally. Recent work on Cholesky, LU, and LDL^T has been single-solve focused. Supporting true batching of these new factorizations would require redesigning kernel dispatch and memory layout.

**Context**: The project name promises batching, but recent commits show scalar solve paths. If batching becomes a priority for LU/LDL^T, it's not a quick feature addition—it requires revisiting kernel design and solver scheduling.

### LU GPU Offload Completion Reveals Platform Divergence (2026-02-23)
**Insight**: Moving LU operations to GPU (commits 55948b7, 8ac0a35, d9abcd9) exposed that different GPU platforms require fundamentally different kernel strategies. CUDA's flexible threading model and Metal's fixed threadgroups force different computational orderings. A single "generic" LU kernel doesn't exist—each backend needs its own carefully tuned implementation.

**Context**: The final move to GPU (d9abcd9) completing the LU expansion shows that backend-specific optimization isn't optional. Porting between CUDA and Metal meant redesigning block traversal order, memory access patterns, and synchronization primitives. This pattern likely applies to future GPU work—assume platform-specific kernels are the norm, not the exception.

### GPU Profiling Requires Backend-Specific Instrumentation (2026-02-23)
**Insight**: After completing GPU-accelerated factorizations, observability became critical. Metal and CUDA expose profiling mechanisms differently: Metal uses `MTLCommandBuffer` GPU timing and `MTLCaptureManager` for .gputrace files (Xcode GPU debugger), while CUDA relies on external `nsys` profiling. **Context**: Commit 2332dcd added per-kernel logging via env vars (BASPACHO_METAL_PROFILE=1) and GPU capture support. This revealed that "verify GPU execution" isn't trivial—you need backend-specific tooling. When adding future GPU work, profiling instrumentation should be part of the kernel implementation strategy, not an afterthought.

### Fast Symbolic Analysis: Index Sorting Is Essential for Correctness (2026-02-25)

### Supernode Merging & Level-Set Scheduling Enables Concurrent GPU Dispatch (2026-02-27)
**Insight**: Commit a09b15e implements SupernodeMerger (177 lines) with two-stage clustering: (1) merge adjacent supernodes within computational cost thresholds (fusable work identification), (2) build level-sets ordered by topological dependencies. SupernodeMergerTest (326 lines) validates correctness across matrix shapes and supernode configurations. Level-set scheduling groups supernodes by depth, enabling asynchronous dispatch—supernodes at the same level have no data dependencies and can execute concurrently on the same GPU stream.

**Context**: After completing single-solve GPU-accelerated factorization (Cholesky, LU, LDL^T), the next optimization target is batched execution. However, batching here doesn't mean multiple matrices—it means executing multiple independent supernodes concurrently on the same GPU. Supernode merging reduces kernel launch overhead (merge small adjacent supernodes into larger computational units), while level-set scheduling identifies parallelism within the elimination tree. This is the foundation for future GPU kernel batching: instead of launching each supernode sequentially, batch level-sets (all supernodes at depth k) as a single grouped dispatch. This pattern generalizes to asynchronous dispatch: once level-sets are known, GPU command buffers can be built to execute all level-k work without waiting for CPU to issue subsequent commands. The test coverage (326 lines) validates that merging decisions and level construction are correct across varied matrix structures—essential because merging heuristics and topological ordering interact subtly with sparse structure blockings.

### Fill Tolerance Guard: Edge Case of Zero Tolerance (2026-02-27)
**Insight**: Commit 5425f30 changes the fill tolerance guard from `relaxedFillTol > 0.0` to `relaxedFillTol >= 0.0`. The original logic treated zero tolerance as "disabled"—when fillTolerance=0.0, merging was skipped entirely. The fix redefines zero: it now means "merge only if the fill increase is exactly zero (free merge)."

**Context**: Edge cases in numeric thresholds are easy to miss. A fillTolerance > 0 clearly means "accept up to this much fill increase," but zero was ambiguous: does it disable merging, or allow only perfect merges? Commit 5425f30 documents the intent (zero = strict, > 0 = relaxed) through the guard change and corresponding BASPACHO_CHECK validation. This teaches that threshold parameters should be explicit about boundary conditions. When adding Settings with numeric guards, define what happens at zero, negative, infinity, etc. Tests should exercise these edge cases—zero tolerance merging is a valid (albeit conservative) strategy.

### GPU Dispatch Overhead Forces Threshold-Based Hybridity (2026-02-27)
**Insight**: Commit c2b751a replaces Metal CPU fallbacks for potrf (Cholesky) and trsm (triangular solve) with MPS GPU operations. **Context**: GPU acceleration isn't "replace CPU with GPU everywhere"—it's selective offload when size justifies dispatch overhead. The lesson: design threshold parameters into GPU operations from day one, expose them as environment variables, and test across the size range where transitions occur. ### Metal Encoder Lifecycle: Decoupling Buffer and Encoder Creation (2026-02-27)
**Insight**: Commits c2b751a and 7600472 fix a critical bug in encodeKernel(): the command buffer was created once and reused across custom kernels and MPS operations. After MPS operations (which internally end the encoder), subsequent encodeKernel() calls failed because the encoder was invalid. Fix: decouple buffer allocation from encoder creation—allocate the buffer once, but create a fresh encoder for each operation.

**Context**: Metal's MTLCommandBuffer and MTLRenderCommandEncoder have tight lifecycle coupling. MPS operations (MPSMatrixDecompositionCholesky, MPSMatrixSolveTriangular) are "black boxes" that manage their own encoders—they end the encoder when done. If you try to reuse the encoder afterward, it's invalid. This is a subtle graphics-API issue that only manifests when mixing custom kernels and MPS in a single solve pipeline. The pattern: treat each heterogeneous operation (custom kernel, MPS, etc.) as encoder-scoped; don't assume encoder state persists across different operation types. For Metal GPU code integrating multiple libraries (custom kernels + MPS), document encoder boundaries explicitly and create fresh encoders per operation.

### Deferred GPU Synchronization Reduces Command Submission Overhead (2026-02-28)
**Insight**: Commit d8590c1 optimizes batched Metal operations by deferring GPU synchronization points. Instead of syncing after each level-set dispatch in the batched solve pipeline, collect sync decisions and issue them in batches. This reduces CPU command buffer submission overhead when solving multiple systems with grouped GPU operations.

**Context**: Batched factorization/solve (09b144e) measures multi-system throughput—however, each level-set dispatch was followed by explicit GPU sync, stalling CPU waiting for GPU completion. Deferring sync allows CPU to issue multiple level-set dispatches before waiting, enabling GPU-CPU pipelining. This validates the async dispatch foundation (c471761): even without fully asynchronous scheduling, batching sync points improves throughput. The pattern: when designing GPU operations for batching, separate command generation (CPU) from synchronization (wait points), allowing overlap. Deferred sync is a precursor to true async dispatch—both defer blocking the CPU.

**Application**: This optimization applies to multi-system scenarios (100+ matrices in batched solve). For single-system solves, sync overhead is dwarfed by computation. Measurement shows when deferred sync becomes valuable: profile single-system vs batched, identify CPU stall points, then defer sync selectively. CI batched benchmarks (09b144e) should quantify throughput improvement from this change to validate that GPU-CPU overlap justifies code complexity.

### Post-Factorization Pivoting Can't Recover from Reordering-Induced Zero Pivots (2026-02-28)
**Insight**: Commit e406e6a implements static pivoting (diagonal perturbation after getrf) to stabilize factorization when pivots are zero/near-zero. **Application**: Static pivoting remains useful as diagnostic tool (exposing pivot count imbalance) and safety mechanism (prevents immediate crashes), but don't rely on it as stability solution for ill-conditioned problems. Use preprocessing-based approaches (MC64, BTF reordering) upfront instead.
